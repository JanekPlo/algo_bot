## Bonus — retroactive correction of Session 1's audit

This is the most strategically important outcome of the cleanup session, and the reason 5c (the `long_term` "dead code" item) did not need a deletion but a documentation fix.

**What Session 1 wrote.** In `docs/reference/modules/strategy-bghtrend-pullback.md` (Gate 4) and `docs/reference/modules/indicators-xtrender.md`, the audit recorded that the entry filter in bghtrend is `short_t3`, and that `long_term` is computed-but-unused dead code in the xtrender module.

**What is actually true.** In `_compute_indicators`, the unpack is `_x_short, x_long, _x_t3, ...`. By tuple position, `x_long` binds to **`long_term`** (position 1). The `_xtr_ok` gate that the strategy actually uses in `next()` reads `x_long`, not `_x_t3`. Same for the stale-exit logic. So `long_term` is the strategy's primary momentum filter, and `short_t3` only drives the dots detection used elsewhere (in-profit dot exit timing).

**How the truth surfaced.** The operator supplied the original Pine Script of B-Xtrender (@Puppytherapy) as an independent oracle while writing `tests/test_xtrender.py`. The Pine source labels `longTermXtrender` as the "B-Xtrender Trend" component — the regime-detection line — with the T3-with-dots line giving timing. Bghtrend uses both exactly that way. Variable names map 1:1 to tuple positions; a `short_t3` filter on a pullback would block legitimate entries (which is also a semantic check that fails for the wrong assignment).

**What got fixed in the docs.** Strategy docstring (entry filter #3), Gate 4 + stale-exit + indicators table in `strategy-bghtrend-pullback.md`, At a glance / Formula / tuple table / Interpretation / Edge cases / Consumers in `indicators-xtrender.md`, glossary `Deadzone` entry. **Zero behavioural change** — the code was correct from the start; only the documentation was wrong.

**Lesson for Phase 2 onward.** Session 1's code reading assumed an unpack order rather than verifying it against an independent source. Decision 5b (standalone tests for the indicator using a hand-implemented oracle, not pandas re-application) was framed as a coverage gap, but it turned out to be the verification that caught the documentation bug. Every deep reference doc that describes the semantics of an indicator-strategy connection in this project should ship with an ortogonal verification — independent oracle, not a self-consistent re-read of the same code. This applies in particular to the future Session 3 microstructure module (slippage and funding adjustments will be subtle enough that "I read it carefully" is not enough; reproduce the math from a Binance docs example).

Decyzje do uzgodnienia w sesji (PRZED implementacją — opcje + trade-offs):

1. SCOPE MODULE — extension istniejącego vs nowy moduł:
   a) Extension `algo_bot/engine/backtester.py` — funkcje slippage()

   b) Nowy moduł `algo_bot/microstructure.py` — top-level, pure functions

   Sugestia: (b) nowy moduł top-level. Pattern identyczny do
   algo_bot.risk z Decyzji E. Pure layer testowalne osobno, dobrze
   namespaced (slippage + funding + ewentualnie market_impact_estimator
   w przyszłości).

2. SLIPPAGE MODEL — gdzie aplikujemy i jak:
   a) On entry/exit price — modyfikuj fill price w backtester.py
      przed użyciem przez backtesting.py engine. Najmniejsza
      ingerencja w PnL math, najbardziej intuicyjne.
   b) Post-hoc na trades_pnl — odejmij slip × notional od każdego
      trade'a po close. Prostsza implementacja, ale traci sub-trade
      resolution (przy bracket orderach SL/TP może źle aplikować).
   c) Hybrid: on entry/exit (a) dla market orders, post-hoc (b) dla
      limit orders gdy backtester nie symuluje precyzyjnie fill
      probability.
   Sugestia: (a). bghtrend (per Sesji 1) używa market orders na entry
   i bracket SL/TP. Modyfikacja entry price w Strategy.next() jest
   minimalnie inwazyjna i daje deterministyczne PnL.

3. SLIPPAGE MAGNITUDE — stały vs size-aware:
   a) Stały bps (np. 5 bps na entry, 5 bps na exit, total 10 bps
      round-trip). Najprostszy, ROADMAP Fazy 2 sugeruje "5-10 bps".
   b) Linear w size: slip = base_bps + alpha * (notional / liquid_depth).
      Wymaga liquid_depth estimate (czyli orderbook history albo
      proxy z volume).
   c) Square-root market impact (Kyle's lambda): slip = c * sqrt(notional).
      Klasyk akademii, mniej empirycznie potwierdzony dla crypto.
   Sugestia: (a) stały bps konfigurowalny przez CLI, z default
   ~5 bps per side. Size-aware (b)/(c) jako future flag jeśli sweep
   pokaże że bghtrend trade'uje sufficient notional żeby market
   impact mattered (>$50k zwykle).

4. SLIPPAGE DIRECTION — symetryczny vs asymmetric:
   Crypto perp orderbook na Binance USDT-M ma asymmetryczne spready
   między longing i shorting w okresach skrajnego funding rate.
   a) Symmetric: stały bps oba kierunki, oba sides
   b) Asymmetric: long side ma wyższy slip gdy funding rate >> 0
      (longs płacą shorts, więc longing ma "psychological premium"
      reflektowany w orderbook)
   Sugestia: (a) symmetric na MVP. Empiryczna walidacja asymmetric
   wymaga orderbook depth history — nie mamy w bot_data/.

5. FUNDING — gdzie aplikujemy:
   Binance USDT-M perp funding settlement co 8h (00/08/16 UTC).
   a) Per bar accrual — accrued_funding = position_notional * funding_rate
      * (bar_seconds / 28800). Każdy bar dodaje frakcję funding.
   b) Per settlement event — naliczać tylko co 8h dla pozycji
      otwartych w momencie settlement. Bliżej rzeczywistości
      (Binance robi point-in-time settlement), ale wymaga match
      timestampów z 00/08/16 UTC.
   c) Per trade close — sumować funding paid przez cały okres
      trade'a, odejmij od trade PnL na exit.
   Sugestia: (b) per settlement event. Najbliżej rzeczywistości.
   Wymaga skanu trade journal: dla każdej pozycji listę
   funding_timestamps które trafiły w window [entry, exit] i
   aplikacja funding rate z tych konkretnych settlement'ów.

6. FUNDING SOURCE — historical vs synthetic:
   a) Historical funding rate z Binance (kanoniczne)
      — endpoint /fapi/v1/fundingRate, historia od listing per symbol.
      Fetch ~7000 settlements per symbol (8h × 7 lat). Wymaga
      nowego algo-fetch-funding command + processed CSV.
   b) Synthetic constant ~0.01% per 8h — average historical, mniej
      precyzyjny ale zero infrastructure
   c) Hybrid: historical jeśli dostępne, synthetic fallback z
      logger.warning
   Sugestia: (a) historical. Funding ma duże tail events (Luna,
   FTX) które synthetic average przegapia, a stress test Fazy 2
   ich potrzebuje. Plus fetch jest mały (~7000 rows × 2 symbols),
   szybki.

7. FUNDING STORAGE:
   a) bot_data/processed/binance_<SYMBOL>_funding.csv — analogicznie do

   b) Single bot_data/processed/binance_funding.csv z kolumną symbol
   c) JSON dict per symbol
   Sugestia: (a). Spójność z OHLCV naming + data_loader pattern.

8. CLI FLAGS — argumenty:
